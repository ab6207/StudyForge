# StudyForge

Paste your notes or name a topic → get interactive flashcards or a multiple-choice
quiz, generated by an LLM and rendered as real React UI (not a chat window).

Built for a frontend internship take-home assignment.

## Structure

```
study-forge-project/
├── frontend/     React + Vite app (the UI)
└── backend/      Node + Express API (talks to the AI provider + optional MongoDB)
```

Each folder is a fully independent app with its own `package.json` — you
`npm install` and run them separately. They only communicate over HTTP:
the frontend calls the backend's `/api/generate` and `/api/sessions`
routes.

## Quick start (both, locally)

Open two terminals.

**Terminal 1 — backend**
```bash
cd backend
npm install
cp .env.example .env
# edit .env and add GROQ_API_KEY (free at console.groq.com/keys)
npm start
```
Backend runs at **http://localhost:5050**.

**Terminal 2 — frontend**
```bash
cd frontend
npm install
npm start
```
Frontend runs at **http://localhost:5173** and proxies `/api/*` calls to
the backend automatically in dev (see `frontend/vite.config.js`) — you
don't need to set `VITE_API_URL` locally.

`MONGODB_URI` in the backend `.env` is optional. Without it, everything
works except "Save & share link", which returns a clear disabled message
instead of crashing.

## Deploying to Vercel

Because frontend and backend are separate apps, deploy them as **two
separate Vercel projects** pointing at the same repo:

**Backend project**
1. New Vercel project → same GitHub repo → set **Root Directory** to `backend`.
2. Add environment variables: `GROQ_API_KEY` (required), `MONGODB_URI`
   (optional), `CORS_ORIGIN` (set once you know the frontend's deployed URL).
3. Deploy. `backend/vercel.json` routes all `/api/*` traffic to
   `backend/api/index.js`, which re-exports the same Express app used
   locally — no code differs between environments.
4. Note the deployed URL, e.g. `https://study-forge-backend.vercel.app`.

**Frontend project**
1. New Vercel project → same repo → set **Root Directory** to `frontend`.
2. Add environment variable `VITE_API_URL` = the backend URL from above.
3. Deploy (framework preset: Vite, auto-detected).
4. Go back to the backend project's `CORS_ORIGIN` env var and set it to
   the frontend's deployed URL, then redeploy the backend so CORS allows it.

No API key ever reaches the browser — the frontend only ever calls the
backend's `/api/*` routes, and the Groq key lives solely in the backend's
environment.

### Alternative: one deployment instead of two
If you'd rather not manage two Vercel projects, the backend also runs
fine on Render/Railway/Fly (`npm start` in the `backend` folder is a
normal long-running Express server — `server/index.js` calls
`app.listen()`). Point `VITE_API_URL` at wherever it ends up.

## How bad AI output is handled

This was the main design focus, per the assignment brief. The pipeline
(all in `backend/server/`) is:

1. **Prompt constraints** — the system prompt (`lib/groqClient.js`)
   demands raw JSON in an exact shape, plus Groq's `response_format:
   json_object` as a second line of defense.
2. **Extraction with fallbacks** (`lib/validate.js::extractJson`) — try
   `JSON.parse` directly, then strip markdown code fences, then fall back
   to slicing out the outermost `{...}` block. If nothing parses, the
   request fails with `PARSE_ERROR` before it reaches the frontend.
3. **Schema validation** (`validateStudySet`) — checks the parsed object
   has an `items` array and filters out any individual item with the
   wrong shape (missing fields, wrong types, `correctIndex` out of
   range). If every item is malformed → `SCHEMA_ERROR`; if only some are,
   the valid ones still render.
4. **Typed error codes over the wire** — `BAD_INPUT`, `CONFIG_ERROR`,
   `TIMEOUT` (25s abort), `UPSTREAM_ERROR`, `EMPTY_RESPONSE`,
   `PARSE_ERROR`, `SCHEMA_ERROR` — each mapped to a specific, honest
   message in the frontend (`frontend/src/hooks/useAIGenerate.js`)
   instead of a generic "error occurred."
5. **Stale-response guard** (in the same hook) — every request gets an
   incrementing id, and the previous in-flight request is aborted when a
   new one starts. A slow request that somehow resolves after a newer one
   has its result discarded rather than overwriting the current UI.
6. **No crashes on bad data** — `Flashcards`/`Quiz` components only ever
   render already-validated items.

Test it by submitting garbage input (a single character, random symbols)
or by watching the network tab while spamming "Generate" — only the
latest request's result should ever land in the UI.

## Known limitations

- No streaming — the full JSON response is parsed before anything
  renders (listed as a stretch goal, not attempted).
- Session save/share is a minimal demo: reloading a shared link shows a
  confirmation toast rather than fully rehydrating the flashcard/quiz
  view — the storage and retrieval work, the rehydration UI doesn't.
- No automated tests.
- Groq's smaller/faster models occasionally return fewer items than
  requested for very short input; the UI reflects however many valid
  items actually come back rather than padding to match the requested count.
- CORS defaults to allowing all origins unless `CORS_ORIGIN` is set —
  fine for a demo, worth tightening for anything real.
